# JD 확인과 Notion 등록 — 지원서 작성 스킬 작업본

## 실행 순서

1. 로그인 후 원래 공고를 열고 공고명, 회사, 마감 날짜·시간, 고용 형태, 근무지와 JD 제공 방식을 확인한다.
2. 웹 JD 또는 첨부 PDF 원문을 먼저 펼쳐 읽는다. PDF 목차와 세부 페이지를 구분하고, 조직/팀 소개·수행업무·자격요건·우대사항 및 추가 안내를 확인한다. 직무 목록만 보고 먼저 지원 직무를 묻지 않는다.
3. 동시에 사용자가 지정한 Notion 데이터베이스의 현재 속성·옵션·조회 필터와 기존 페이지 본문 형식을 읽는다. 직전 맥락과 스키마가 동일하면 이미 확인한 내용을 재사용한다.
4. 회사명, 구체적 포지션, 채용 시기, 원문 링크/공고 식별자와 JD 내용으로 기존 등록을 확인한다. 원문 링크는 페이지 댓글까지 읽어 확인한다. 한 목록 뷰에 안 보인다는 이유만으로 미등록으로 판단하지 않는다. 상태·날짜 필터로 기존 항목이 가려질 수 있다.
5. 독립적으로 지원하는 직무가 하나면 그 직무로 진행한다. 여러 개면 JD 내용을 확인한 뒤 사용자가 선택하게 한다. 기존 Notion 항목은 선택 확인의 근거로 보여줄 수 있지만, 현재 지원할 직무가 확정된 것으로 간주하지 않는다. 단일 포지션 내부의 여러 수행업무를 여러 채용 직무로 잘못 세지 않는다.
6. 선택한 포지션이 미등록이면 기존 데이터베이스에 새 항목을 생성한다. 신규 등록이 현재 요청에 포함되어 있을 때만 생성한다. 기존 항목이 있으면 중복 생성하지 않고 이어서 사용한다. 사용자의 메모·지원 현황·면접 기록을 덮어쓰지 않는다.
7. 생성 후 다시 읽어 속성·본문과 댓글의 공고 링크가 제대로 저장되었는지 확인한다. 직무 선택 대기 중에는 임의의 포지션으로 등록하지 않는다.

## PDF 처리

- 사용자가 지정한 방식으로 PDF를 확인한다. 공고에 실제 노출된 첨부 링크를 먼저 사용한다.
- 첨부 링크가 다운로드 방식이면 브라우저 표시와 다운로드를 구분하여 보고한다. 브라우저 보안 정책으로 열기가 막히면 로컬 서버·다른 브라우저·우회 URL 등으로 차단을 우회하지 않는다.
- 웹 표시가 불가능할 때는 그 한계를 알리고, 정상 다운로드된 원문을 PDF 도구로 읽어 진행 가능한 스크랩을 계속한다. 페이지 번호를 보존하고 선택에 필요한 관련 페이지의 렌더링도 확인한다. 로컬로 읽은 결과를 웹에서 열어 확인했다고 보고하지 않는다.
- 텍스트 추출 순서만으로 필수/우대 조건을 분류하지 않는다. 실제 페이지 제목과 시각적 순서를 확인한다. 이미지형 PDF면 시각 확인이나 적절한 OCR을 사용하고, 미확인 항목을 창작하지 않는다.

## 채용달력 매핑 예시

실제 데이터베이스 주소·연결 ID는 사용자 제공 링크나 비공개 설정에서 찾고, 공유 스킬에는 기록하지 않는다. 아래는 일반 설정 예시이며, 다른 DB에서는 현재 스키마를 우선한다.

| Notion 항목 | 저장할 내용 |
| --- | --- |
| 회사명 | 회사명. 페이지 제목 속성이다. |
| 공고명 | 지원하는 구체적인 포지션명. |
| 직무명 | 기존 선택지에 맞춘 직무 분류. PM, 서비스기획, Project Manager, 전략, 기타 등. 공고명과 혼동하지 않는다. |
| 구분 | 경력/신입/인턴/계약직 등 기존 옵션과 공고 근거에 맞춘다. 경력 구분과 고용 형태가 둘 다 필요하면 본문에 고용 형태를 별도 보존한다. |
| 연차 | 확인한 기존 항목은 요구 경력 범위의 하한을 숫자로 사용한다. 범위나 예외 조건은 본문에 보존한다. 숫자가 명시되지 않았으면 임의로 0을 넣지 않는다. |
| 지원서 마감일 | 사용자의 작성 방식에 따라 날짜만 저장한다. 시간은 입력하지 않으며, 기존 항목에 시간이 없다는 이유로 보완을 요구하지 않는다. |
| Open date | 마감이 없는 공고는 체크하고 지원서 마감일에 공고를 등록한 날짜(Asia/Seoul)를 넣는다. 마감일이 있으면 체크하지 않고 실제 마감 날짜를 넣는다. 원문 접근 실패로 마감을 확인하지 못한 경우를 마감 없는 공고로 간주하지 않는다. |
| 해외 | 해외 공고 여부. 근무지 근거로 판단한다. |
| 결과 | 신규 관심 공고는 미지원. 지원서 초안이나 임시저장만으로 심사중으로 바꾸지 않는다. |
| 1차/2차 면접일, 피드백 | 신규 스크랩 시 비워두고, 기존 값은 보존한다. |

## 페이지 본문 스크랩

- 확인한 기존 페이지들은 원문의 제목과 불릿 구조를 보존하여 내용을 직접 담고 있다. 회사/조직 소개, 수행업무, 자격요건/유관 경험, 우대사항을 해당 원문 제목에 맞춰 정리한다.
- 주요 구역은 실제 Notion 제목 블록(제목 2 또는 제목 3)으로 구분해 빠르게 찾을 수 있게 한다. 구역 안의 세부 업무는 불릿과 하위 불릿으로 계층을 보존한다. 단순 굵은 글씨만으로 모든 구역 제목을 대체하지 않는다. 현재 대상 DB의 스키마와 사용자 방식을 따른다.
- 사용자가 열거한 네 항목만 강제로 남기지 않는다. 원문에 있는 지원 조건, 포트폴리오 필수, 근무지, 고용 형태, 전형·접수 안내 등 지원 판단에 필요한 정보도 보존한다.
- 원문에 조직명이 없으면 조직 역할 설명만 쓰고 팀명을 만들어내지 않는다. 출처 전용 본문 섹션이나 PDF 파일명·페이지 번호·확인일을 필수 입력 항목으로 추가하지 않는다. 공고 원문 링크는 아래 댓글 방식으로 기록한다.
- 사실 스크랩과 해석·지원 적합성 평가를 구분한다. 이 단계에서는 사용자 경력에 대한 추정을 덧붙이지 않는다. 적합성 추천을 요청받은 경우 별도로 Drive 경험 원문을 확인한다.

## 공고 링크 댓글

- 공고 원문 URL을 댓글로 기록하는 설정을 선택한 경우에 적용한다. 신규 공고를 등록하면 원문 링크를 페이지 수준 댓글로 남긴다.
- 기존 항목은 댓글을 먼저 확인한다. 같은 공고 링크가 있으면 그대로 사용한다. 없으면 사용자 지시에 따라 링크 댓글을 추가한다.
- 링크만으로 충분하며, 별도 출처 보고서나 긴 설명을 붙이지 않는다. 댓글 생성 결과가 불확실하면 재조회하여 중복 생성을 막는다.
