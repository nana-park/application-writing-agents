# 지원서 입력란용 경험 정리

같은 경험을 지원 회사의 직무에서 읽을 수 있는 문안으로 정리한다. 연구 초록을 복사하거나 자소서형 포부를 붙이기보다, 무엇을 왜 어떻게 수행했고 무엇을 확인했는지 빠르게 읽히게 만든다. 기존에 잘된 경험정리를 기준으로 필요한 부분만 바꾼다.

## 입력과 범위

회사·직무·JD, 입력란 이름과 필수 필드·글자 수·줄바꿈 허용 여부를 확인한다. 현재 대화나 기존 작업에 있으면 재질문하지 않는다. 양식을 모르면 빠진 항목만 묻고, 확인한 범위의 정리본을 먼저 제시한다. 기존 지원 전략·기업조사는 재사용하고 이 작업 때문에 전체 자소서 사이클을 다시 실행하지 않는다.

별도 입력란이 있는 서지정보와 상세 설명을 분리한다. 연구·논문은 제목, 게재지/학회, 발행기관, 게재 상태·날짜, 저자순위, ISSN 등 실제 요구 필드만 채운다. 온라인 선공개와 권호 발행, 학회 발표와 저널 게재를 구별한다. 특허는 출원과 등록, 발명자 역할을 구별한다.

## 작성 재료의 우선순위와 실행 순서

담당업무, 프로젝트, 연구, 논문·특허, 활동 등 모든 입력란에 아래 순서를 적용한다. JD와 입력 조건은 시작할 때 확보하되 JD 표현으로 문안을 재구성하는 단계는 재료 탐색 뒤인 4번이다.

1. **지원전략 참고:** 기존 Google Docs 기업조사 보고서의 해당 회사 탭에서 직무 분석, 지원전략, 강조 역량과 경험 연결 제안을 실제로 읽는다. 현재 지정 문서에서 찾고 없으면 회사명으로 검색한다. 보고서가 없거나 접근 불가하면 짧게 알리고 확인 가능한 JD로 진행하며 기업조사 전체를 자동 재실행하지 않는다. 현재 JD·사용자 우선순위와 충돌하면 현재 지시를 우선한다.
2. **Notion 회사별 작성 이력 전체 수집:** 작성 대상인 담당업무·프로젝트·연구 등의 구역에서 다른 회사에 사용한 날짜별·회사별 history와 하위 토글 본문을 모두 읽어 재료로 모은다. 최신본 하나만 읽거나 사용자에게 재질문받을 때만 과거본을 읽지 않는다. 목록·제목만 확인하고 본문을 읽은 것으로 처리하지 않는다. 현재 대상 구역과 해당 경험의 모든 회사별 이력을 포함하되 무관한 개인 자료까지 확대하지 않는다. 이전 제목, 업무명, 구체 행동, 방법, 산출물, 성과와 강점 표현을 비교해 쓸 재료를 확보한다. 이미 읽은 변하지 않은 이력은 재사용한다. 이 단계는 과거의 '히스토리는 필요할 때만 확인' 제한보다 우선한다.
3. **경험자료 탐색:** 2번에서 부족한 역할·방법·근거는 경험정리와 Drive 경력기술서에서 찾아 읽고 보완한다. 연구·논문·특허는 허용된 포트폴리오와 주요 연구과제 파일도 활용하며 논문 원문 재검증으로 확대하지 않는다. 현재 문안에 없다고 실제 경험이 없다고 판단하지 않는다. 같은 경험의 회사별 버전을 별도 경험으로 세거나 다른 프로젝트의 일을 해당 연구에 섞지 않는다. 수치·역할 충돌은 보존 기준본과 현재 사용자 지시를 따르고 강한 값만 골라 합치지 않는다. 다른 경험이 적합하면 별도 소재로 제안한다.
4. **JD 원문 표현 적용:** 확보한 재료를 지원전략에 따라 선택하고 `지원전략 → 회사별 history 재료 → 경험 근거 → JD 원문 표현 → 반영 문구`로 내부 대응시킨다. 실제 수행에 맞는 JD 명사구·업무 표현을 그대로 대괄호 제목, ① 업무명, 상세내용, 시사점의 수정 가능 구역에 배치한다. 일반적인 동의어로 약화하지 않는다. 짧은 업무명 제한에 맞지 않으면 상세내용에 원문 표현을 살린다. 같은 단어를 반복하거나 보존 구역을 바꾸지 않는다. 새로운 관점의 초안은 근거 안에서 구성하고 수행 범위가 불명확할 때만 채팅에서 사실관계를 확인한다. 근거 없는 산업 경험·기술·성과를 만들지 않는다.

압축 후 JD 원문을 다시 대조해 핵심 표현 누락, 불필요한 동의어 치환, 단어 반복, 근거 없는 키워드 삽입을 점검한다. 이 재료 목록·대응표·검색 기록은 Notion 문안에 붙이지 않는다.
## 사실 확인과 회사별 관점

### 지정 Notion 기준본의 형식과 값 우선

아래 자료 제한은 개인 경험의 사실 근거 범위다. JD 원문과 기존 Google Docs 기업조사·지원전략 보고서는 별도의 전략 입력으로 반드시 확인하며 이 제한 때문에 제외하지 않는다.

논문·특허의 JD 맞춤 정리는 사용자 지정 Notion 정리본과 Google Drive의 경력기술서, 포트폴리오, 주요 연구과제 파일만 확인한다. Notion은 문안과 보존 구역의 기준이며, 지정한 세 종류의 Drive 자료는 수행내용의 실제 역할·방법·산출물을 보완할 때만 사용한다. 이미 확인한 자료는 재사용하고 매번 전부 다시 읽지 않는다. 논문 PDF·게재 원문·학위논문·학술대회 원문·특허 원문·외부 학술 사이트·기타 Drive 자료로 검색 범위를 확대하거나 표본·통계·날짜를 다시 검증하지 않는다. 사용자가 별도 사실 검증을 요청할 때만 그 요청 범위에서 확대한다. 허용 자료가 없거나 충돌하면 Notion 값을 임의 교체하지 않고 필요한 사항만 채팅에서 확인한다. 이 자료 범위는 아래 일반적인 Drive 원문 확인 규칙보다 우선하며, 다른 경력·프로젝트 정리의 자료 범위는 바꾸지 않는다.

사용자가 Notion 정리본을 기준으로 회사별 문안을 편집하라고 하면 해당 정리본을 편집 기준으로 사용한다. 특히 연구의 보존 구역과 수치·날짜·서지정보는 사용자가 별도로 사실 검증이나 변경을 요청하지 않는 한 원문대로 유지한다. 이 작업을 자동으로 논문 재검증·버전 비교 보고서 작성으로 확대하지 않는다. 프로젝트의 Drive 조회 의무가 적용되더라도 그 조회를 보존 구역의 값 교체 권한으로 해석하지 않는다. 충돌이 실제 작업을 막으면 채팅에서 필요한 사항만 짧게 확인하고 Notion 본문에 감사 기록을 추가하지 않는다.

- 사용자가 방금 정정한 사실을 우선하고, 연결된 Google Drive의 연구 원문·경력 자료로 역할·방법·수치를 확인한다. Google Docs 현재 경험정리, Notion 경험정리 및 이력서·경력기술서는 해당 작업의 소스 우선순위를 따른다. 이미 읽은 유효한 근거는 재사용한다.
- 회사별·시기별 토글에 같은 연구가 있어도 별도 경험으로 세지 않는다. 제목·연구 대상·기간 등으로 같은 경험을 식별한다. 이전 지원용 표현은 참고 문안이지 원문 사실보다 우선하는 근거가 아니다.
- 버전 사이 표본 수, 효과 크기, 날짜, 역할이 다르면 강한 수치만 섞지 않는다. 모집 인원과 유효 표본, 기준선과 비교군, 증감률과 퍼센트포인트를 구분한다. 해결되지 않은 차이는 제출 문안 밖의 확인사항으로 남긴다.
- JD가 업무 개선을 강조하면 요구사항·프로세스·검증 결과를, 사용자 경험을 강조하면 사용맥락·설계·평가를 앞세울 수 있다. 이는 관점 전환이며 실제 업무·산출물·권한을 추가하는 것이 아니다.
- 설문이나 인터뷰를 수행했다고 제품을 출시한 것으로, 개선안을 제안했다고 매출이나 제도 변화를 직접 만든 것으로 바꾸지 않는다. 팀 산출물과 본인 수행을 구분한다. 기술 용어는 원문과 실제 역할로 입증될 때만 사용한다.

## 문안 구성

### N+500자 초안 후 압축

최종 제한이 N자이면 먼저 내부 확장 초안을 N+500자 분량으로 작성하고, 이후 N자 이내로 줄인다. 처음부터 제한에 끼워 맞추며 방법·판단·수치를 누락하지 않는다. 확장 초안도 확인된 사실만 사용하며 분량을 채우려고 경험이나 숫자를 만들지 않는다. 근거가 부족하면 부족한 범위를 밝힌다. 제목·공백·줄바꿈은 실제 입력란의 계산 기준을 적용한다. 압축 순서는 입력란별 작성 규칙을 따르고 핵심 역할·방법·성과·인과관계를 보존한다. 확장본은 작업용이며 기본 반환·제출 문안은 검수한 N자 이내 최종본이다. 확장본 요청 시 별도 표시해 제공한다. 단어·오탈자만 고치는 요청에는 전체 재작성을 하지 않는다. 기존 writing 예산 안에서 실행한다.

먼저 입력란 유형을 구분한다. 경력 담당업무와 경험·프로젝트에는 반드시 [입력란별 작성 규칙](references/entry-writing-rules.md)을 읽고 적용한다. 학력의 통합 주요성과와 활동·수상도 해당 참조의 구분을 따른다. 아래 연구용 구조를 경력·프로젝트에 일괄 적용하지 않는다. 기존 application-form-writer의 작성 규칙을 이 참조로 이관했으며, 현재 사용자 지시와 실제 양식이 과거 사이트별 예외보다 우선한다.

### 연구 원문 보존과 수정 범위

기존 연구 정리본의 상위 번호 항목명과 순서, 보존 구역의 하위 항목을 유지한다. 연구 수행내용 안의 ①~④ 업무명은 고정 항목명이 아니라 JD 맞춤 편집 대상이다. 기본 구성은 `개요 → 연구배경(문제정의, 목표설정) → 연구 수행내용 → 연구결과 → 시사점`이다. 회사별 JD 맞춤 수정 대상은 맨 위 대괄호 요약 제목, 연구 수행내용, 시사점이다. 대괄호 제목은 공식 논문명이 아니며 실제 연구에서 드러나는 직무 관련 행동과 강점을 중심으로 조정한다. 공식 논문명과 서지정보는 유지한다. 개요, 연구배경의 문제정의와 목표설정, 연구결과의 기존 문구와 수치는 그대로 유지한다. 시사점을 성과로 바꾸거나 별도 성과 항목을 추가하지 않는다. 항목을 합치거나 생략하지 않는다. 현재 사용자가 특정 구역의 변경을 명시적으로 요청한 경우에만 그 범위의 예외를 적용한다.

N+500자 확장과 압축은 대괄호 요약 제목, 연구 수행내용, 시사점 안에서 한다. 보존 구역을 포함한 전체 제한을 계산하되 분량을 맞추려고 보존 구역을 고치지 않는다. 보존 구역만으로 제한을 넘거나 사실·수치 충돌을 발견하면 문안 밖에서 충돌과 필요한 선택을 알린다. 임의로 수치를 교체하지 않는다. 기존본이 없을 때만 아래 구성을 초기 틀로 사용하며, 기존본이 있으면 그 항목 구성을 우선한다.

[직무 관련 행동과 연구 대상을 보여주는 제목]

1. 개요
2. 연구배경: 문제정의, 목표설정
3. 연구 수행내용
4. 연구결과
5. 시사점

시사점은 기본 두 개의 짧은 목록으로 작성하고 각 항목은 띄어쓰기 기준 10어절 이내로 제한한다. 첫 항목은 연구에서 확인하거나 도출한 내용을 `검증` 또는 `제안`으로, 둘째는 직무와 연결되는 설계·활용 방향을 `제시`로 끝낸다. 장문 설명이나 포부를 덧붙이지 않는다. 기존 Notion 기준본에 정책 변화 기여 등 실질 성과가 명시돼 있으면 그 문구와 연도는 그대로 보존하고 일반적인 시사점으로 대체하지 않는다. 이 보존 항목은 두 항목·10어절·종결어 형식보다 우선하며, 필요하면 추가 항목으로 유지한다. 다만 사용자가 든 예시만으로 특정 연구의 새로운 성과를 만들어 넣지는 않는다.

- 수행내용은 '사용맥락 분석: 관찰 자료를 분류해 요구사항 도출'처럼 짧은 기능명 뒤에 구체 행동을 적는다. 방법명만 나열하지 않고 무엇을 판단하거나 검증했는지 연결한다.
- 연구 수행내용은 `① 업무명: 핵심 행동과 산출물(도구) - 세부 예시, 지표 목록` 형식을 사용한다. 각 번호는 별도 줄 또는 문단으로 쓰고 여러 단계를 한 문단에 이어 붙이지 않는다. 도구는 필요할 때 괄호로, 긴 예시나 평가항목은 공백을 둔 짧은 하이픈 ` - ` 뒤로 분리한다. 긴 대시를 쓰지 않는다. 세부 열거에는 가운데 점을 되도록 쓰지 않고 쉼표나 `및`을 사용한다. 모든 항목에 예시나 도구를 억지로 붙이지 않는다.
- 압축할 때 번호별 줄바꿈과 구역 구분은 유지하고 각 항목 안의 중복 표현을 줄인다. Notion 저장 후에도 단계별 줄바꿈이 유지됐는지 확인한다. 줄바꿈을 지원하지 않는 실제 양식만 예외로 구분해 처리한다.
- 인터뷰 인원·시간, 평가항목 수, 프로토타입 수 등은 수행 규모로 표시하고 성과 개선 수치와 구별한다. 유의한 관계와 인과, 제안과 구현을 구별한다.
- 연구결과는 그대로 보존한다. 시사점의 내용은 JD에 맞게 수정하여 확인된 연구결과가 지원 직무의 문제 해결과 고객경험 설계에 주는 의미를 드러낸다. 실제로 수행하지 않은 산업·제품 경험이나 성과를 추가하지 않으며 자소서형 포부나 검수용 단서를 붙이지 않는다. `시사점`이라는 상위 항목명과 순서는 유지한다.
- 연구에서는 대괄호 요약 제목, 수행내용의 용어·강조점, 시사점의 내용을 JD에 맞춰 조정한다. 상위 번호 항목명과 나머지 보존 구역은 바꾸지 않는다. `① 업무명: 상세내용`에서는 콜론 앞 업무명과 뒤 상세내용 모두를 실제 수행 근거 안에서 JD에 맞춰 검토·수정한다. 예를 들어 사용맥락 분석을 고객 탐색여정 분석으로 바꿀 수 있으나, 실제로 하지 않은 업무로 재명명하지 않는다. 기존 표현이 이미 적합하면 유지할 수 있으며 무조건 동의어로 치환하지 않는다. 직무 키워드를 모두 넣기 위해 문장을 늘리지 않는다. 구체 방법과 수치를 버리고 추상적인 전문성 표현으로 바꾸지 않는다.
- 기본은 복사 가능한 한 안이다. 요청하지 않은 A/B, 별도 회사조사, 과도한 사례 탐색은 추가하지 않는다. 제한이 있으면 실제 글자 수와 공백·제목·줄바꿈 포함 기준을 확인한다.

## 반환과 검수

사용자에게 제공하거나 Notion 연구 토글에 저장하는 기본 결과는 실제 쓸 문안뿐이다. JD에 맞춘 대괄호 요약 제목과 기존 번호 항목으로 바로 시작하며, 지원직무·적용 우선순위·공고 링크·범위 설명, `복사용 문안 — N자 / 제한`, `서지정보 — 별도 입력란 참고`, `출처·검수 메모 — 복사 제외`, `사실 확인·버전 차이`, 보존 작업 설명을 새로 덧붙이지 않는다. 기존 개요에 있는 서지정보는 보존하지만 별도 안내 구역으로 중복 생성하지 않는다. 글자 수와 근거는 내부에서 확인하고, 저장 완료·글자 수 등 필요한 작업 보고는 채팅에서 짧게 알린다. 사용자가 별도 보고서를 요청한 경우만 예외다.

과장 여부와 측정 범위는 내부에서 검수하되 `실제 매출 증가와 구분` 같은 검수용 단서를 성과 항목에 넣지 않는다. 본문에는 구매의도 등 실제 측정 지표명과 필요한 비교 조건을 정확하게 쓴다. 출처 확인, 미확인 사항과 검수 메모는 복사할 제출 문안 밖에 둔다. 양식이 연구 한계를 직접 요구하면 해당 항목에 답한다.

필드 충족, 사실·수치·서지정보 일치, 본인 기여, 수행내용과 결과의 연결, 직무 관점, 분량을 확인한다. 멀티에이전트 실행 시 현재 writing 5분 예산과 수정 후 독립 재검수 규칙 안에서 처리한다. 이 스킬이 추가 단계나 새 에이전트를 요구하지는 않는다.

## Notion 보관과 웹 입력의 경계

이 스킬은 경험 문안 작성과 회사별 Notion 보관을 담당한다. application-form-writer는 완성 문안의 채용 사이트 입력과 임시저장을 담당한다. 채용공고 JD의 Notion 등록과 경험 문안 보관을 혼동하지 않는다.

1. 현재 요청이나 이어지는 작업에서 Notion 저장이 승인되어 있으면 다시 허락을 묻지 않고 진행한다. 문안만 요청한 경우 임의로 원본을 수정하지 않는다. 저장 위치가 불명확할 때만 대상 페이지를 확인한다.
2. 저장 직전에 대상 페이지와 기존 토글을 읽어 사용자의 직접 수정사항을 보존한다. 원본, 다른 회사 지원본, 이번 수정 대상의 경계를 확인한다.
3. 기존 페이지 구조에 맞춰 `담당업무 - 날짜 - 회사명`, `연구 - 날짜 - 회사명` 등 회사별 토글과 항목별 하위 토글로 보관한다. 날짜와 회사는 확인된 값만 쓰고, 같은 대상이 있으면 중복 생성하지 않는다.
4. 공통 원문과 다른 회사 버전은 덮어쓰지 않는다. 같은 회사 문안의 후속 수정은 대상만 갱신하되 기존 내용은 수정 전 버전으로 보존한다. 원문을 직접 수정하는 요청도 보존본을 확보한 뒤 반영한다. 페이지 전체 교체 대신 해당 항목만 변경한다.
5. 토글 안에는 실제 문안만 저장한다. 출처·글자 수·검수 메모·버전 차이 보고서를 별도 구역으로 덧붙이지 않는다. 원문 보존용 이력은 기존 보관 위치를 따르고 본문에 작업 로그를 쌓지 않는다. 사용자가 직접 바꾼 역할·성과 수치를 이전 값으로 되돌리지 않고, 충돌하면 채팅에서 필요한 차이만 확인한다.
6. 저장 후 대상 토글의 제목과 본문을 재조회해 실제 문안, 끝부분 누락, 글자 수, 원문 보존을 확인한다. 도구 성공 응답만으로 검증 완료라고 하지 않는다. 결과에는 페이지 링크와 토글명, 변경 범위 및 검증 상태를 남긴다.

저장이 실패하거나 재조회가 불가능하면 작성 완료와 저장 미완료를 분리해 알리고 복사 가능한 문안을 제공한다. 결과가 불명확한 저장을 재시도하기 전에는 현재 내용을 조회해 중복을 피한다. 멀티에이전트에서는 작성자가 저장 대상과 문안을 메인에 전달하고, 메인이 저장·재조회 결과까지 확인한다. 실제 채용 사이트 입력·임시저장은 application-form-writer로 넘기며 최종 제출은 별도 요청 범위다.

## 적용 한계

일반 작성·보관 규칙이며 개인별 결과물과 조회 로그는 공개하지 않는다. 입력 양식과 원문 보존 범위, 사용 가능한 소스, 외부 저장 권한은 현재 요청에서 확인한다. 실제 작성·저장 성공은 해당 작업에서 검증해야 한다.
