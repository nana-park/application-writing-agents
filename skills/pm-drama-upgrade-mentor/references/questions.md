# 질문과 분기

아래는 읽어 내려갈 설문이 아니다. 현재 글의 선택을 가장 크게 바꾸는 질문 하나를 골라 사용자의 말에 맞게 고쳐 묻는다. 여기의 문구는 개인 수업의 인용이 아닌 일반화한 질문 예시다.

## 시작할 때

| 빈칸 | 질문 예시 | 답을 쓰는 곳 |
|---|---|---|
| 지원 기준 | 어떤 직무의 어떤 문항에 넣을 경험이야? | 독자가 확인할 역량과 범위 |
| 전체 인상 | 읽는 사람이 너를 어떤 동료로 기억했으면 해? | 지원자 컨셉 |
| 컨셉 근거 | 그 모습을 보여주는 행동이나 동료 피드백이 있어? | 희망 이미지와 사실의 접점 |
| 피할 오해 | 적극성을 보여줄 때 독단적으로 읽힐까 걱정되는 부분이 있어? | 표현과 보완 맥락 |
| 이번 글의 역할 | 이 경험에서는 무엇을 제일 확실하게 보여주고 싶어? | 중심 주장 |
| 다른 글과 중복 | 다른 문항에서 이미 충분히 보여준 강점은 뭐야? | 사례와 디테일 배분 |
| 표현의 경계 | 이 표현은 면접에서 네 말로 설명할 수 있어? | 책임 범위와 문체 |

지원 수준은 실제 기대 업무와 맡았던 범위로 확인한다. “주니어지만 경험의 폭이 넓음”, “맡은 범위에서 스스로 판단함”, “피드백을 빠르게 반영함”은 동시에 성립할 수 있다. 조용한 말투를 수동성으로, 적극적인 말투를 리더십으로 단정하지 않는다.

## 매 턴 질문을 선택하는 절차

1. **문항 해석과 핵심 주장부터 점검하고 수정할 구절을 잡는다.** AI 강점을 요구하는데 일반 협업담으로 답하는 등 방향이 틀렸다면 문장 디테일보다 주장과 사례 선정을 먼저 바로잡는다. 방향이 맞으면 가장 중요한 구절 하나를 골라 이번 컨셉에서 무엇을 증명해야 하는지 정한다.
2. **답변으로 확인된 것과 빈 연결을 구별한다.** 대상·행동 / 방법·조건 / 선택 이유 / 실제 반영 / 검증·개인 역할 중 이미 설명된 것을 건너뛴다. 이 항목들은 고정 질문 순서가 아니다.
3. **가장 중요한 빈 연결에 질문 하나를 고른다.** 무슨 일을 했는지도 모르면 행동을 먼저 복원한다. 행동이 구체적이면 이유나 반영 방식으로 이동한다. 사실 충돌이나 역할 과장이 드러나면 이를 우선 확인한다.
4. **사용자 답변을 받고 분기한다.** 아래 답변별 분기표를 사용한다. 처음 선택한 질문 계열을 끝까지 채우려고 하지 않는다.
5. **충분히 확보되면 문장으로 시험한다.** 해당 구간의 as-is/to-be와 살아난 판단을 보여주고, 핵심 해석이 맞는지 확인한다. 부족한 근거는 문장 밖에 남긴다.

내부 메모 예: `대상 구절 / 증명할 역량 / 확인된 사실 / 빈 연결 / 이번 질문의 목적 / 본문 반영 또는 보류`. 사용자에게 매번 이 양식을 채우게 하지 않는다.

## 답변을 받은 뒤의 분기

| 사용자의 답변 상태 | 다음 질문 또는 처리 | 넘어가는 기준 |
|---|---|---|
| “분석·개선·검토했다”만 반복 | 실제로 열어본 자료나 조작한 화면 하나를 떠올리게 한다 | 대상과 관측·행동 하나가 설명됨 |
| “특정 조건의 자료를 골랐다” | 왜 그 조건이 문제를 찾는 단서였는지 묻는다 | 선별 기준과 목적이 연결됨 |
| “시간이 없어서”, “정확하게 하려고” | 어떤 마감이나 혼입 요인 때문에 어떤 판단이 어려웠는지 좁힌다 | 제약이 선택에 미친 영향이 설명됨 |
| 용어·도구·기능 이름만 나온다 | 그 안에서 실제로 무엇이 입력·변경·출력됐는지 쉬운 말로 묻는다 | 이름 없이도 작동을 설명할 수 있음 |
| 방법과 이유는 있지만 후속 행동이 없다 | 발견 결과를 바탕으로 무엇을 바꿨는지 묻는다 | 관측에서 제품·운영 결정으로 이어짐 |
| 팀이 했다는 답으로 개인 역할이 불분명 | 본인이 만든 기준·자료·합의와 다른 사람이 실행한 일을 구분한다 | 개인 기여를 과장 없이 문장에 쓸 수 있음 |
| 다른 팀에 요청한 것으로 끝난다 | 어떤 조건을 맞춰야 상대가 수행할 수 있었는지 묻는다 | 자료·권한·리소스·일정 중 실제 조정한 내용이 확인됨 |
| 성과 수치만 나온다 | 무엇을 어떤 기간·기준으로 집계한 값인지 묻는다 | 수치의 뜻과 비교 범위를 보존할 수 있음 |
| 설명이 길고 기술적이다 | 먼저 끝까지 이해하고 판단에 필요한 요점을 추린다 | 세부 설명을 자르지 않아도 핵심 원리를 요약할 수 있음 |
| 멘토의 해석을 정정한다 | 정정 내용을 우선 반영하고 기존 가설을 폐기한다 | 잘못 가정한 질문을 반복하지 않음 |
| “모르겠다”, “기억 안 난다” | 관련 문서·장면이 떠오르는지 부담 없는 단서 질문을 한 번 시도하거나 보류한다 | 추가 단서가 없으면 미확인으로 남기고 다른 부분 진행 |
| 이미 충분히 구체적이다 | 더 묻지 않고 부분 수정과 비교로 이동한다 | 아래 종료 기준 충족 |

“왜?”만 반복하지 않는다. 사용자가 말한 구체 명사를 질문에 다시 사용해 답변 범위를 좁힌다. 생각했던 대안과 사후에 떠오른 대안도 구분한다. “이 방식을 쓰지 않았으면?”이라는 질문은 당시 제약을 설명하기 위한 보조 질문이며 가상의 실패를 실제 사건으로 기록하지 않는다.

## 다섯 가지 심화 경로

아래 화살표는 가능한 후속 질문의 연결이다. 한 턴에 화살표 전체를 질문하지 않는다. 사용자 답변에 필요한 다음 지점만 선택한다. 개인 역할은 어느 경로에서든 모호해지면 확인한다.

### 1. 관측·선별 기준을 판단으로 연결

자료나 현상 → 골라본 대상 → 기준의 근거 → 확인된 패턴 → 바뀐 결정.

- 첫 질문: 어떤 자료를 보고 문제를 확인했어?
- 특정 구간·조건을 골랐다면: 왜 그 조건이 문제 신호라고 봤어?
- 기준이 타당해 보이면: 실제 확인 결과도 그 예상과 맞았어?
- 결과까지 있으면: 그 결과 때문에 무엇을 다르게 하기로 했어?

단서와 확정 진단을 구별한다. 짧은 이용 시간이나 낮은 빈도 같은 프록시만으로 실제 불만·오류가 입증됐다고 쓰지 않는다. 선택 기준이 이미 설명됐으면 사용 도구나 쿼리 자체로 불필요하게 깊게 들어가지 않는다.

### 2. 재현·검증 방법의 필요성을 확인

확인할 현상 → 기존 환경의 한계 → 바꾸거나 고정한 조건 → 관측 방식 → 확인 결과.

- 첫 질문: 무엇을 확인하려고 테스트를 따로 했어?
- 새 환경을 만들었다면: 기존 환경으로 확인하면 무엇을 구별하기 어려웠어?
- 조건을 나눴다면: 어떤 조건을 다르게 했고, 나머지는 어떻게 유지했어?
- 단계별로 봤다면: 어디의 결과를 무엇과 비교해서 문제 지점을 좁혔어?

새 계정이나 여러 케이스가 등장한다고 통제 실험으로 단정하지 않는다. 실제 고정·변경 조건과 관측 목적을 듣고 명칭을 정한다. 테스트하지 않은 조건이나 음성 결과까지 만들어 넣지 않는다.

### 3. 기능을 실제 작동 흐름으로 설명

사용자·운영자 → 조작 대상 → 바뀌는 정보·상태 → 반영 시점 → 해결되는 불편.

- 첫 질문: 사용자가 어디에서 무엇을 할 수 있게 된 거야?
- 화면만 설명했다면: 그 조작 이후 실제로 바뀌는 정보는 뭐야?
- 데이터 변경까지 설명했다면: 그 변경이 다음 동작에는 언제 어떻게 반영돼?
- 작동이 명확하면: 그중 네가 정한 흐름이나 기준은 어디까지야?

내부 데이터 구조를 직접 설계하지 않았어도 운영 정책이나 수정 흐름을 정의한 기여는 설명할 수 있다. 전문성을 강조하려고 백엔드·코딩 업무를 본인의 일로 바꾸지 않는다.

### 4. 협업 요청을 실행 가능하게 만든 조건 확인

상대가 할 일 → 필요한 조건 → 실제 조정 → 합의·인계 → 수행 확인.

- 첫 질문: 상대 팀이 그 요청을 처리하려면 무엇이 필요했어?
- 권한이나 자료 제약을 말하면: 그 제약은 어떻게 풀어서 전달했어?
- 업무 부담을 말하면: 기존 업무와 병행하도록 어떤 범위를 조정했어?
- 합의가 됐다면: 어디까지 수행됐는지는 어떻게 확인했어?

반대·갈등·설득이 있었음을 전제하지 않는다. 별도 조정 없이 통상 업무로 처리됐다면 그대로 받아들인다. 협업 디테일이 중심 컨셉과 무관하면 짧은 배경 설명용으로 보류한다.

### 5. 선택의 당위성과 성과를 연결

당시 목표 → 가능한 대응 → 선택 제약·기준 → 선택한 범위 → 실제 결과·측정.

- 첫 질문: 그 대응을 우선한 이유가 뭐야?
- “빠르니까”라고 하면: 어떤 시점까지 무엇을 해결해야 했어?
- 공통화나 구조 변경을 했다면: 개별 대응을 계속하면 어떤 문제가 남는다고 봤어?
- 성과가 등장하면: 그 값이 직접 보여주는 변화는 무엇이야?

결과가 좋아졌다는 사실만으로 선택 이유를 역으로 지어내지 않는다. 당시 판단과 나중에 얻은 교훈을 나눈다. 평가에서 선택 이유가 약하다고 나오면 먼저 기존 답변에 그 이유가 있는지 확인하고, 없을 때 이 경로로 돌아온다.

## 언제 질문을 멈출지

현재 구절에 대해 다음 조건이 충족되면 부분 수정으로 넘어간다.

- 누가 무엇을 했는지와 본인의 기여 범위가 분명하다.
- 글에서 주장하려는 판단에 필요한 방법·조건과 선택 이유를 실제 답변으로 설명할 수 있다.
- 그 행동이 다음 결정·제품 동작·검증 결과 중 무엇으로 이어지는지 보인다. 부분 구간마다 최종 사업 성과까지 반복 확보할 필요는 없다.
- 독자가 이해하는 데 필요한 핵심 해석이 미확인 가정에 의존하지 않는다.

충분한지 확인하려고 모델이 빈칸을 채운 요약을 먼저 내놓지 않는다. 확인된 사실만으로 핵심을 짧게 정리하고 의미 있는 해석이 추가됐다면 사용자에게 맞는지 묻는다. 남은 정보가 문장의 의미를 바꾸지 않는 부수적인 도구명·횟수라면 더 캐묻지 않는다.

기억이나 자료가 부족하면 질문 실패를 사용자의 경험 부족으로 평가하지 않는다. 해당 주장을 낮추거나 제외하고, 확인 가능한 문장부터 다듬는다. 확보한 내용은 본문 핵심 / 후속 설명용 / 미확인으로 구별해 두며 개인별 기록을 스킬에 저장하지 않는다.

## 초안의 증상에 따른 첫 질문

초안이 거칠수록 사용자가 전문적인 답변을 이미 준비했으리라 기대하지 않는다. 아래처럼 문장에서 빠진 내용을 짚고 실제 기억을 꺼낼 수 있는 질문으로 바꾼다. 다음 예시는 가상의 대화이며, 각 질문 뒤에는 반드시 사용자의 답을 기다린다.

- 초안: “테스트를 많이 해서 오류를 고쳤습니다.”
- 첫 반응: “테스트했다는 건 보이는데, 어떤 조건에서 문제가 생기는지 좁혀간 과정은 아직 안 보여. 처음 오류를 발견했을 때 어떤 상황에서 다시 나타나는지 확인했어?”
- 사용자가 “조건을 바꿔봤다”고 답하면: “그때 하나씩 바꿔본 조건은 뭐였어?”
- 특정 조건을 답하면 그 답을 바탕으로 비교 결과와 판단을 묻는다. 답변 전에 통제 실험이나 원인 분석을 수행했다고 이름 붙이지 않는다.

| 보이는 증상 | 다음 질문의 초점 | 답에 따른 처리 |
|---|---|---|
| 회사 소개와 배경이 길다 | 이 정보를 모르면 네 판단을 이해할 수 없는 지점이 어디야? | 판단에 필요한 맥락만 남기기 |
| 문항의 AI·직무 요구와 경험이 어긋난다 | 이 질문에 답하지 못하면 채용자가 네게 무엇이 없다고 의심할까? | 중심 주장과 사례부터 다시 선택 |
| 문제가 누구에게나 해당한다 | 그때 특히 문제가 됐던 일정·사용 조건·운영 제약은 뭐였어? | 실제 조건 확보; 없으면 긴박함을 꾸미지 않기 |
| 공부·조사했다는 보고뿐이다 | 조사해서 무엇을 알아냈고, 그래서 어떤 결정을 바꿨어? | 자료 열람을 판단의 근거로 연결 |
| 기준 없이 데이터를 분석했다 | 어떤 데이터를 제외하거나 골랐고, 그 기준은 왜 타당했어? | 관측→분류→판단 연결 |
| 테스트했다는 말뿐이다 | 기존 환경으로 확인할 수 없어서 따로 통제한 조건은 뭐였어? | 재현 조건과 검증 목적 연결 |
| 해결책이 당연해 보인다 | 다른 방법 대신 이 방법을 먼저 택한 이유는 뭐야? | 대안·제약·우선순위 회수 |
| 도구 이름만 나온다 | 그 도구로 얻은 정보가 제품의 어떤 결정으로 이어졌어? | 도구 나열을 구체적 기여로 전환 |
| 교육시간·처리 건수만 크다 | 이 숫자는 노력·범위·품질·제품·사업 중 무엇을 직접 보여줘? | 숫자의 층위를 분리하고 과잉 결론 제거 |
| 구현 흐름이 생략돼 있다 | 사용자의 행동 이후 어떤 정보나 상태가 바뀌고 결과에 반영돼? | 입력·변경·동작·사용자 가치 연결 |
| 협업이 “요청했다”로 끝난다 | 상대 팀은 어떤 조건을 충족해야 움직일 수 있었고, 너는 무엇을 조정했어? | 역할·리소스·일정·합의 범위 확인 |
| 팀 성과에 개인이 묻힌다 | 그중 네가 직접 정한 기준과 다른 팀이 결정한 부분은 각각 뭐야? | 개인의 판단을 드러내되 타인의 기여 유지 |
| 단순 제안처럼 읽힌다 | 네가 제시한 안은 어디까지 채택됐고 구현·검증에는 어떻게 관여했어? | 제안·결정·실행·검증 구분 |
| 숫자는 큰데 뜻이 불명확하다 | 이 수치는 무엇 중 무엇의 비율이고, 언제와 언제의 비교야? | 범위·기간·분모 확인 후 표현 결정 |
| 기업 성과가 개인 성과로 이어진다 | 네 작업과 그 성과 사이에서 직접 확인할 수 있는 변화는 뭐야? | 직접 결과와 후속 기여 분리 |
| 배운 점이 상투적이다 | 이후 비슷한 상황에서 실제로 달라진 판단이나 행동이 있어? | 재사용 가능한 원칙으로 정리 |

사용자 답변에 새 단서가 있으면 표의 다음 행으로 이동하지 말고 그 단서를 따른다. 민감한 수치나 이름은 정확한 원문 제출을 압박하지 않고 공개 가능한 범위에서 확인한다.

## 선택이 갈리는 순간

### 전체 인상과 개별 글의 강조점

두 안이 각각 어떤 근거를 살리고 무엇을 덜어내는지 설명한다. 예: 판단을 보여주는 안과 협업 과정을 보여주는 안. 문항과 현재 컨셉에 맞는 쪽을 추천한 뒤 사용자가 의도를 정하도록 묻는다. 정답이 둘뿐인 것처럼 말하지 않는다.

### 주도성 표현

주도형 컨셉을 고르는 것과 “주도했다”는 동사를 쓰는 것은 다르다. 실제 결정권, 제안의 채택, 합의 형성, 실행 범위를 확인한다. “반대했다”는 표현이 원래 의도를 흐리면 무엇을 지키고 무엇을 바꾸려 했는지 묻는다. 실제 갈등을 숨기거나 모든 반대를 협업으로 미화하지 않는다.

### 독자와 기술 깊이

비전문 독자용 본문에는 판단을 이해하는 데 필요한 기술 디테일을 남긴다. 직무 전문가용이면 실제 검증 조건이나 작동 원리를 더 깊게 다룰 수 있다. 전문용어를 늘리는 것과 전문성을 보이는 것을 혼동하지 않는다. 어려운 단어를 쓸지보다 어떤 판단을 증명할지를 먼저 정한다.

### 구조·분량·제목

성과가 먼저 나오는 안은 결과와 역량을 빠르게 전달한다. 전환점부터 시작하는 안은 동기와 성장의 연결에 적합할 수 있다. 추천 구조의 효과를 설명하고 중요한 방향 차이가 있을 때만 묻는다.

삭제할 디테일이 컨셉의 핵심 증거라면 조용히 빼지 않는다. 본문에 남길 판단과 후속 설명으로 보류할 세부 사항을 구분한다. 제목은 본문이 안정된 뒤 필요할 때 제안한다. 성과 요약·판단의 차별점·맥락 강조 중 무엇을 앞세울지 맞추며, 숫자나 자극적인 제목을 필수로 만들지 않는다.

## 답변 이후의 턴

새로 확인된 요점을 한두 문장으로 해석하고, 왜 채용 근거로 강하거나 약한지 판단한다. 문장을 시험해볼 근거가 생겼다면 해당 부분만 수정해 보여준다. 아직 중요한 빈 연결이 있을 때만 핵심 질문 하나를 묻고 멈춘다. 충분하면 추천·수정·평가로 진행한다. 해소된 문제를 다른 표현으로 반복 질문하거나 전체 자소서를 매번 다시 출력하지 않는다.
