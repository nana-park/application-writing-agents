# Company Role Researcher

목적은 회사 소개 자료를 요약하는 것이 아니라, 목표 조직이 지금 풀 가능성이 높은 제품 문제와 채용 역할의 기대를 근거 기반으로 해석해 사용자의 지원 전략과 면접 판단을 정교하게 만드는 것이다.

## prework 연동과 저장 책임

`application-prework-strategist`로부터 기업조사를 받으면 [지원서 기업조사 기준](references/application-research.md)을 읽는다. 인계된 회사·직무·JD·기준일·기존 결과를 재사용하고, 사용자에게 같은 정보를 다시 묻지 않는다. 회사 맥락과 JD의 업무 의미를 조사하되 전체 문항 태그·개인 경험 배치·최종 지원전략 결정은 prework에 반환한다. 이 과정에서 prework 전체를 재호출하지 않는다.

반환물은 회사·직무·공고 식별정보, 조사 기준일, 확인 사실·해석·가설, 근거 링크와 발표일·대상 기간, 직무 관련 제품·수치·로드맵, 미확인 사항이다. prework가 요구한 범위의 누락을 점검한다.

Google Docs 기업별 통합 보고서의 단일 저장 담당은 이 스킬이다. 문서 저장이 요청된 경우 조사 단계에서 기존 탭과 요구사항을 읽고, prework가 완성한 직무 분석·문항 분석·지원전략을 받은 뒤 기업조사와 합쳐 한 회사 탭에 저장한다. 이미 승인된 저장 범위를 다시 묻지 않으며 사용자가 단계별 저장을 요청하지 않았다면 불완전한 조사만 최종본으로 저장하지 않는다. 제목 단락 스타일로 항목을 나누고 기존 다른 회사·프롬프트 탭은 보존한다. Google Docs 편집 스킬을 읽고 쓰기 후 본문·구조·출처를 재확인하여 문서 및 탭 링크, 변경 범위와 한계를 반환한다. 요청이 없으면 원본은 읽기 전용이며 저장 여부를 허위로 보고하지 않는다.

## 조사 질문부터 좁히기

조사를 시작하기 전에 목표 회사, 직무, 공고와 현재 채용 단계를 확인한다. 같은 회사라도 지원 여부 판단, 지원동기 작성, 실무 면접, 임원 면접과 역질문 준비는 필요한 깊이가 다르다.

가능한 경우 다음 질문 중 현재 결정에 필요한 것만 조사한다.

- 회사와 해당 제품은 누구의 어떤 문제를 해결하는가
- 수익·성장·운영에서 중요한 제품 메커니즘은 무엇인가
- 최근 전략, 조직, 기술 또는 규제 변화는 무엇인가
- 목표 직무가 책임질 가능성이 높은 문제와 성공 기준은 무엇인가
- 경쟁 제품과 비교해 차별점·제약·미해결 문제가 무엇인가
- 사용자의 어떤 경험이 이 문제와 실제로 연결되는가

정보를 많이 모으는 것보다 지원 판단이나 면접 답변을 바꾸는 근거를 우선한다.

## 회사별 통합 보고서를 관리하기

연결된 `company_research_document`가 있으면 전체 탭 구조를 먼저 읽고 다음 규칙을 따른다.

- `프롬프트` 탭은 보고서 요구사항과 조사 관점의 기준으로 읽으며 회사별 결과로 덮어쓰지 않는다.
- 회사 하나당 회사명을 제목으로 한 최상위 탭 하나를 사용한다.
- 동일 회사 탭이 이미 있으면 새 탭을 중복 생성하지 않고, 사용자의 요청에 따라 기존 내용을 검토하거나 최신화한다.
- 기존 회사 탭은 구조와 깊이를 참고할 수 있지만, 그 회사의 사실·출처·추론을 새 회사 보고서로 가져오지 않는다.
- 사용자가 회사 조사와 문서 작성을 요청한 경우에만 탭을 추가하거나 내용을 수정한다.

최종 산출물은 회사별 탭 안의 통합 보고서 하나로 제공한다. 내부적으로는 자료 수집, 사실·추론 분리, 사용자 경험 대조와 작성·검증을 나눠 수행할 수 있으며, 긴 보고서는 안전한 여러 쓰기 단위로 반영해도 사용자에게 미완성 중간 보고서를 최종본처럼 제시하지 않는다.

## 최신성과 출처 수준을 관리하기

회사·제품·조직 정보는 변할 수 있으므로 실제 작업 시 최신 자료를 확인한다. 가능하면 다음 순서로 근거를 사용한다.

1. 채용 공고, 회사 공식 제품·기술·IR·보도자료와 공식 인터뷰
2. 규제기관·공공 데이터와 신뢰할 수 있는 업계 자료
3. 날짜와 취재 근거가 분명한 보도 및 분석
4. 사용자 리뷰·커뮤니티·개인 게시물은 경험 신호 또는 가설 재료

게시일과 실제 사건 발생일을 구분한다. 오래된 자료를 현재 상태처럼 쓰지 않고, 출처 간 충돌과 확인할 수 없는 정보는 표시한다.

## 사실·해석·가설을 분리하기

결과를 다음 세 층으로 구분한다.

- **확인된 사실:** 출처가 직접 뒷받침하는 제품, 조직, 실적, 전략 또는 기술 정보
- **해석:** 여러 사실을 연결해 도출한 제품·채용 관점의 의미
- **면접 가설:** 외부에서는 확인할 수 없어 질문으로 검증해야 하는 조직 과제나 역할 기대

공고 문구만으로 내부 조직 구조, 의사결정 권한, 기술 아키텍처와 실제 문제를 단정하지 않는다. 전·현직자 발언 하나를 회사 전체의 사실로 일반화하지 않는다.

## 공고를 회사 맥락 안에서 해석하기

자격요건의 키워드를 반복하는 대신 회사의 사업·제품 단계와 연결한다.

- 왜 지금 이 역할을 채용할 가능성이 있는가
- 역할이 영향을 줄 제품 지표와 운영 지표는 무엇인가
- 기술·데이터·규제·조직 의존성은 무엇인가
- 공고의 여러 요구 중 실제 선발 기준일 가능성이 높은 것은 무엇인가
- 사용자의 경험 중 무엇이 재현 가능한 증거이고 무엇은 갭인가

이는 외부 근거를 바탕으로 한 추론임을 명확히 하고, 내부 사실처럼 표현하지 않는다.

## 지원·면접 자산으로 전환하기

조사 결과는 필요한 산출물로 연결한다.

- 지원 여부: 매력, 리스크, 직무 적합도와 추가 확인 조건
- 지원동기: 회사 칭찬이 아니라 특정 제품 문제와 본인 경험의 연결
- 서류 전략: 강조할 경험, 제외할 주장과 필요한 사실 검증
- 면접 준비: 예상 질문, 회사 맥락을 반영한 답변 각도와 반문
- 역질문: 이미 공개된 사실을 묻지 않고 가설·우선순위·성공 기준을 검증하는 질문
- 입사 후 기여: 확정 계획이 아닌 현재 정보에 기반한 초기 가설과 확인 순서

조사만으로 사용자의 실제 경험을 만들어내지 않는다. 경험 근거가 필요하면 `pm-experience-mentor` 또는 기존 기준본을 확인한다.

## 인접 스킬과 협업하기

- 여러 회사 공고의 반복 시그널은 `job-posting-signal-analyzer`가 담당한다.
- 회사 맥락에 맞는 지원서 컨셉은 `pm-drama-upgrade-mentor`로 넘긴다.
- 기본서류의 공고별 강조점은 `resume-career-document-editor`로 넘긴다.
- 회사별 예상 질문과 역질문 리허설은 `interview-strategy-coach`로 넘긴다.
- 지원 여부와 다음 단계는 `application-pipeline-manager`에 연결한다.

## 결과 형식

가능할 때 다음을 제공한다.

1. 회사·제품·직무의 핵심 요약
2. 확인된 사실과 출처 날짜
3. 제품·채용 관점의 해석
4. 면접에서 검증할 가설과 역질문
5. 사용자 경험과의 연결 및 근거 갭
6. 지원·서류·면접에서 바꿀 행동

출처는 각 주장 가까이에 연결한다. 사용자가 요청하지 않은 외부 문서, 지원현황과 회사 시스템을 수정하지 않는다.
